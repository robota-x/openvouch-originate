# Shufti Pro Integration Brief

This document is a concise reference for integrating our verification flow with **Shufti Pro**.  
It focuses on:

- Core HTTP endpoints we will use
- Request / response shape that our backend should standardise on
- Callback / webhook handling
- Environment and credentials assumptions

Implementation details (language, framework, storage) are left to the engineering team.

## Goals

- Trigger a Shufti Pro KYC flow (document + face) for a user.
- Redirect the user to Shufti’s hosted verification UI (onsite mode).
- Receive an asynchronous callback with the verification result and extracted identity data.
- Optionally query status for idempotency / reconciliation.

## Environments and Credentials

Shufti exposes the same API endpoint in:

- **Test/Sandbox**: used during development and staging.
- **Production**: used for live KYC checks.

Base URL (both environments):

- `https://api.shuftipro.com/`[web:89][web:97][web:100]

Authentication:

- HTTP **Basic Auth** using **Client ID** as username and **Secret Key** as password.[web:89]
- Keys are managed in the Shufti Pro Back Office and should be injected via secrets management.

Conceptual example:

```http
Authorization: Basic base64("<CLIENT_ID>:<SECRET_KEY>")
```

> Treat Client ID and Secret Key as sensitive credentials; never expose them in frontend code or logs.

## High-Level Flow

1. **Create verification request** (server-to-server `POST` to Shufti base endpoint).
2. Receive **initial response** containing:
   - `reference` – our correlation ID
   - `event` – typically `request.pending`
   - `verification_url` – hosted verification page URL
   - optional `error` details if request was invalid[web:90][web:96]
3. Redirect the end user to `verification_url` (frontend concern).
4. Shufti processes document + selfie and calls our **callback URL** with status updates.[web:92][web:94]
5. Backend verifies **response signature**, parses verification result and extracted data.
6. Optionally, backend calls **status endpoint** for reconciliation.

## Core Endpoints

### 1. Create Verification Request

- **Method**: `POST`
- **URL**: `https://api.shuftipro.com/`
- **Auth**: HTTP Basic Auth using client credentials.
- **Body**: JSON payload including general parameters and requested services.[web:89][web:100]

General request fields:

- `reference` (string, required): unique request ID generated by our backend (6–250 chars, alphanumeric). Sent back in all responses.[web:89][web:93]
- `callback_url` (string, required): HTTPS endpoint on our backend to receive server‑to‑server notifications.[web:92][web:94]
- `redirect_url` (string, optional but recommended): user redirect URL after onsite flow (e.g. our “verification complete” page).[web:93]
- `email` (string, optional but recommended): end‑user email address.[web:89]
- `country` (string, optional): ISO 3166‑1 alpha‑2 country code; e.g. `"GB"`.[web:89]
- `language` (string, optional): language code; e.g. `"EN"`.[web:89]
- `verification_mode` (string, optional): commonly `"any"`.[web:89]

For a document + face flow, use Shufti’s **onsite document verification** plus facial biometrics.[web:69][web:91][web:101]

Illustrative payload shape (simplified):

```json
{
  "reference": "<our-unique-ref>",
  "callback_url": "https://our-backend.example.com/shufti/callback",
  "redirect_url": "https://our-frontend.example.com/verification/complete",
  "email": "user@example.com",
  "country": "GB",
  "language": "EN",
  "verification_mode": "any",
  "document": {
    "proof": "",
    "additional_proof": "",
    "supported_types": ["id_card", "passport", "driving_license"],
    "name": "",
    "dob": "",
    "document_number": "",
    "expiry_date": ""
  },
  "face": {
    "proof": ""
  }
}
```

> Field names and nested structures must be finalised against Shufti’s **Document Verification** and **Facial Biometrics** onsite docs.[web:69][web:91][web:101]

### 2. Verification Status Endpoint (Optional)

- **Method**: `POST`
- **URL**: `https://api.shuftipro.com/status`
- **Auth**: HTTP Basic Auth.
- **Body**: includes `reference` (and/or Shufti `token`) to query an existing request’s status.[web:91][web:96][web:97]

Use cases:

- Reconciliation when callbacks fail.
- Idempotency checks (e.g. avoid double‑processing).

## Callback / Webhook Handling

Shufti sends server‑to‑server callbacks to the `callback_url` specified in the request.[web:92][web:94]

Typical callback payload (subset):

- `reference` (string): echoes our request reference.[web:90]
- `event` (string): status indicator, e.g. `"verification.accepted"`, `"verification.declined"`, `"request.pending"`, etc.[web:94]
- `verification_result` (object): per‑service pass/fail (`1` accepted, `0` declined, `null` not processed).[web:90]
- `verification_data` (object): extracted data for each verification service (document, face, address, etc.).[web:90]
- `additional_data` (object): extra extracted fields from documents (e.g. MRZ data).[web:90]
- `info` (object): device/browser and geolocation.[web:90]
- `declined_reason` / `declined_codes` when declined.[web:90]

### Response Signature Verification

Shufti signs responses; verification procedure (as described in Onsite / General docs):[web:69][web:74][web:96]

1. Take SHA‑256 of the **Secret Key**.
2. Concatenate this hashed secret key to the end of the **raw response string**.
3. Take SHA‑256 of the concatenated string.
4. Compare with the `Signature` header value.

Backend must:

- Use the exact raw body as received over HTTP as the input for step 2.
- Reject callbacks where computed signature ≠ Shufti’s `Signature` header.

## Data We Intend to Use

From `verification_data` / `additional_data` we primarily need:[web:69][web:91][web:101]

- **Identity fields**:
  - `first_name`, `last_name` (or equivalents)
  - `dob` (date of birth)
  - optional `place_of_birth` or similar, if present and exposed[web:69][web:90]
- **Document fields**:
  - document type (e.g. passport, id_card)
  - document number
  - issuing country
  - expiry date[web:69][web:91]

Internal mapping target (example):

```ts
interface VerifiedIdentity {
  reference: string;           // Shufti reference
  provider: "shufti";
  status: "accepted" | "declined" | "pending";
  reason?: string;

  firstName?: string;
  lastName?: string;
  fullName?: string;
  dateOfBirth?: string;        // ISO-8601 (YYYY-MM-DD)
  placeOfBirth?: string;       // optional

  documentType?: string;
  documentNumber?: string;
  documentCountry?: string;
  documentExpiry?: string;     // ISO-8601

  rawPayload: unknown;         // full Shufti response for audit/debug
}
```

The exact mapping should be finalised once we have concrete JSON samples from our chosen Shufti flows.

## Error Handling and Events

Key event patterns (see “Response Events” docs for full list):[web:94]

- `request.pending`: request accepted; waiting for user.
- `verification.accepted`: verification completed successfully.
- `verification.declined`: verification completed but failed checks.
- Errors (invalid parameters, auth issues, etc.) are returned with an `error` object.

Backend responsibilities:

- Persist `reference`, status, timestamps on initial request.
- On callback:
  - Verify signature.
  - Upsert/update `VerifiedIdentity` record.
  - Handle duplicate callbacks idempotently (same `reference`).

## Frontend / UX Notes (Non‑Prescriptive)

- Use `verification_url` from the initial response to send the user to Shufti’s onsite verification page (redirect, new tab, iframe, etc.).[web:91][web:96]
- Use `redirect_url` so completion returns the user to an appropriate page in our app.

Exact UX and navigation patterns are up to the frontend team.

## Testing Strategy

- Use Shufti’s **demo/test environment** with test credentials for development; same base URL, different keys.[web:66][web:97]
- Point `callback_url` to a QA / non‑public backend endpoint initially.
- Exercise at least:
  - Successful verification
  - Declined verification (bad/expired doc, face mismatch)
  - Signature mismatch / tampered callback
  - Network failures around callbacks

Before production:

- Confirm with Shufti whether any extra signing / headers apply to our plan.
- Clarify rate limits and timeouts.
- Identify exact fields for place‑of‑birth if we want to rely on them.
